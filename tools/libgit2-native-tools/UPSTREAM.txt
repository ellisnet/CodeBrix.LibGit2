================================================================================
tools/libgit2-native-tools - WHERE EVERY VENDORED TREE CAME FROM
================================================================================

This folder vendors two upstream source trees and one set of upstream build
files. None of them is ever edited. Nothing in any build script here clones,
downloads or otherwise fetches source at build time - see README.txt for the
rule this exists to satisfy. This file records, for each tree, its identity,
its licence, exactly how the copy was made, and how to check it again.

This file sits BESIDE the trees rather than inside them, so libgit2/ and
mbedtls/ contain upstream's files and nothing else.


================================================================================
1. libgit2/ - libgit2 1.9.7 (with upstream's .github/ left out)
================================================================================
Project        : libgit2 - a portable, pure C implementation of the Git core
                 methods
Upstream URL   : https://github.com/libgit2/libgit2.git
Release tag    : v1.9.7 (released 2026-08-13)
Snapshot commit: 49e408b3208bc3093757a1c2db938d3590f3f412 (the commit the
                 v1.9.7 tag names; `git get-tar-commit-id` on the release
                 tarball below prints it)
Commit subject : not recorded - the snapshot was taken from the release
                 tarball, which carries the commit id but not the message
Version header : include/git2/version.h: LIBGIT2_VERSION "1.9.7",
                 LIBGIT2_SOVERSION "1.9"
                 => git_libgit2_version() reports 1.9.7
Why this tag   : the newest libgit2 release when CodeBrix.LibGit2 moved off
                 1.8.6 (2026-11-18); 1.9.7 is a security release of the 1.9
                 line (docs/changelog.md in this tree). Upstream
                 LibGit2Sharp.NativeBinaries is still on 1.8.6 and has no 1.9
                 packaging, so nothing here is adopted from upstream any more.
                 The shipped file names keep its first seven hex digits:
                 git2-49e408b.
Licence        : GPLv2 WITH the libgit2 linking exception - COPYING (in this
                 tree; byte-identical to 1.8.6's), which also carries the
                 licences of the bundled dependencies (zlib, PCRE2, llhttp,
                 ntlmclient, SHA-1 collision detection, wildmatch, winhttp
                 definitions + the full LGPL-2.1 text, ...). Shipped beside
                 every binary as LICENSE-Libgit2.txt. The bundled xdiff's own
                 notices are NOT in COPYING; ../LICENSE-Xdiff.txt (this folder)
                 carries them, verbatim from the file headers, and is shipped
                 beside every binary too.

What is in the tree: ALL of the tagged tree EXCEPT .github/ - 11,897 entries
(11,896 files and one symlink, tests/resources/testrepo-worktree/
link_to_new.txt -> new.txt). That includes tests/ (9,867 entries: the clar
suite and its fixture repositories), so the Windows script's -test switch
(BUILD_TESTS=ON + ctest) works from this copy, and deps/ with every bundled
dependency: chromium-zlib, llhttp, ntlmclient, pcre2, winhttp, xdiff, zlib.
libgit2 has no git submodules at this commit.

WHAT WAS LEFT OUT, AND WHY. Jeremy's standing rule is that his repositories
carry no GitHub workflow files - vendored ones included. Upstream's .github/
folder is therefore NOT part of this snapshot. It held exactly these 10 files
(nothing else in the tree was left out):

    .github/ISSUE_TEMPLATE                       (a file, not a folder)
    .github/actions/download-or-build-container/action.yml
    .github/actions/run-build/action.yml
    .github/release.yml
    .github/workflows/benchmark.yml
    .github/workflows/build-containers.yml
    .github/workflows/documentation.yml
    .github/workflows/experimental.yml
    .github/workflows/main.yml
    .github/workflows/nightly.yml

None of them is used by any build: they drive upstream's own CI. (The 1.8.6
snapshot that this one replaced still carried its .github/, workflows
included; that was the gap this rule closes.)

How the copy was made, 2026-11-18 (the one network use, the download, was
done once beforehand; this folder's builds use no network):

    # the release tarball of the tag, downloaded once:
    #   https://github.com/libgit2/libgit2/archive/refs/tags/v1.9.7.tar.gz
    #   sha256 1a4fbe7589e814777ae76b64734ad80f4ecad22cd33a22682a2aaea4ae5375e7
    #   7,769,162 bytes; git get-tar-commit-id -> 49e408b3208b...
    mkdir <scratch>/vendor-1.9.7
    tar -xzf libgit2-1.9.7.tar.gz -C <scratch>/vendor-1.9.7
    rm -rf tools/libgit2-native-tools/libgit2          # the 1.8.6 tree, whole
    rsync -a --exclude=/.github \
        <scratch>/vendor-1.9.7/libgit2-1.9.7/ \
        tools/libgit2-native-tools/libgit2/

A GitHub tag archive is the tree at the commit: libgit2's .gitattributes has
no export-ignore or export-subst rule, so nothing tracked is dropped or
rewritten by the archive. Afterwards `diff -r -q <extracted tarball>
tools/libgit2-native-tools/libgit2` reported exactly one difference: "Only in
<extracted tarball>: .github".

Tree checksum (run from inside libgit2/; symlinks hashed through their
target), AFTER the removal of .github/:

    find . \( -type f -o -type l \) | LC_ALL=C sort \
        | xargs -d '\n' sha256sum | sha256sum

    fd514ceba60f654b467a95704435f6e39204efde8812ba527c096c8fbad41a33  -

NOTHING IN THE BUILD FETCHES. libgit2's CMake has one download path,
deps/chromium-zlib/CMakeLists.txt (FetchContent of Chromium's zlib), and it is
reached only with -DUSE_BUNDLED_ZLIB=Chromium. Every build here uses
USE_BUNDLED_ZLIB=ON (= deps/zlib) on Linux, Android and macOS, and on Windows
upstream's own default (no system zlib -> deps/zlib), so that code is never
configured. The Linux and Android builds prove it on every run by building
with no network interface.

upstream's own .gitignore files (./.gitignore, tests/resources/.gitignore and
those inside the tests/resources fixtures) are part of the snapshot. For this
tree `git status --ignored --porcelain -- tools/libgit2-native-tools/libgit2`
lists NOTHING: no upstream file is hidden by them, so a plain `git add` of this
folder picks up the whole tree (../.gitignore re-includes what the
repository-root .gitignore would otherwise hide - see its comment).

WHAT CHANGED FROM 1.8.6 IN WHAT IS COMPILED IN (for THIRD-PARTY-NOTICES.txt):

  deps/zlib          1.3 -> 1.3.1 (same zlib licence)

  deps/ntlmclient    still 0.9.0 (inline helpers made C90-clean)
  deps/pcre2         unchanged (10.47)
  deps/xdiff         one fix in xmerge.c; the four licence headers that
                     ../LICENSE-Xdiff.txt reproduces are unchanged
  deps/chromium-zlib, deps/winhttp
                     unchanged (and compiled into no build here)
  src/util/khash.h   GONE - its code lives on, modified, in the new
                     src/util/hashmap.h, which keeps the khash MIT notice
                     (Copyright (c) 2008, 2009, 2011 Attractive Chaos).
                     Neither 1.8.6's nor 1.9.7's COPYING mentions khash.
  src/util/hash/sha1dc, src/util/hash/rfc6234 (sha224-256.c changed, same
                     licence header), wildmatch, rand.c (xoroshiro256**,
                     public domain), the Android-derived basename code
                     unchanged as third-party code
  nothing third-party was ADDED

Project        : Mbed TLS - TLS / X.509 / crypto library
Upstream URL   : https://github.com/Mbed-TLS/mbedtls.git
Release tag    : v3.6.7 (annotated tag da6a8c7b9b8e0c1e236deef2910642657db1a7ec;
                 mbedtls-3.6.7 is a second tag on the same commit)
Snapshot commit: 068ff080b369adfac81509f9b57b2afabaf82dc5

Version        : include/mbedtls/build_info.h: MBEDTLS_VERSION_STRING "3.6.7"
Why this tag   : the newest tag of the 3.6 long-term-support branch on
                 2026-10-17 (`git ls-remote --tags`: v3.6.0 ... v3.6.7; 3.6
                 is the LTS line, and the one libgit2 1.8.6's - and 1.9.7's -
                 src/libgit2/streams/mbedtls.c and util/hash/mbedtls.c are
                 written against; 4.x moved the crypto APIs into
                 TF-PSA-Crypto). NOT upgraded with the move to libgit2 1.9.7
                 (2026-11-18): this tree is unchanged since 2026-10-17.
Submodule      : framework/ = https://github.com/Mbed-TLS/mbedtls-framework
                 at dde0c4a0e448a0552f18817dcea633bb851fd288 (2026-06-24), the
                 commit v3.6.7 records. Vendored too, because a 3.6 checkout
                 without it is incomplete (its CMake and scripts reference
                 framework/).
Licence        : Apache-2.0 OR GPL-2.0-or-later (dual; LICENSE in this tree,
                 which also holds the full Apache-2.0 text). CodeBrix.LibGit2
                 takes it under Apache-2.0. LICENSE is shipped beside the two
                 Android binaries as LICENSE-MbedTls.txt.
Used by        : the two Android builds ONLY (android/build.py), compiled first
                 as STATIC libraries (libmbedtls.a, libmbedx509.a,
                 libmbedcrypto.a) and linked into libgit2-49e408b.so. The
                 Linux builds use OpenSSL at run time, Windows Schannel, macOS
                 SecureTransport - none of them touches this tree.
Generated files: v3.6.7 is a release tag and carries its generated sources
                 (library/error.c, version_features.c,
                 ssl_debug_helpers_generated.c, psa_crypto_driver_wrappers*.
                 ...), so the build runs with GEN_FILES=OFF and needs no
                 Python or Perl.
3rdparty/      : everest and p256-m are compiled as separate static libraries
                 by Mbed TLS's CMake but are OFF in the default configuration
                 (MBEDTLS_ECDH_VARIANT_EVEREST_ENABLED and
                 MBEDTLS_PSA_P256M_DRIVER_ENABLED are commented out in
                 include/mbedtls/mbedtls_config.h, which is used unmodified),
                 are not linked, and android/verify.py records that none of
                 their symbols is in the library.

How the copy was made, 2026-10-17:

        ~/ClaudeHome/libgit2-upstream-scratch/mbedtls/ \
        tools/libgit2-native-tools/mbedtls/

================================================================================
NOT MODIFIED
================================================================================
No file in libgit2/, mbedtls/ or reference-upstream/ has been modified,
renamed, reformatted or deleted, and none ever should be. The one deliberate
omission is libgit2's .github/ folder, left out WHOLE at vendoring time (section
1) - no file inside the snapshot was touched. There is no patch
mechanism in this folder: if a build ever needed a change to upstream source,
the rule is to stop and decide, not to patch quietly. (The two first-run
problems of 2026-10-17 - the image's pcre-devel and the NDK headers' `inline`
under libgit2's strict C90 - were both solved with build options, and 1.9.7
needed no new one; see BUILD-PROVENANCE.txt.)

VERIFYING A SNAPSHOT AGAINST UPSTREAM (optional, needs network)
--------------------------------------------------------------------------------
    git clone https://github.com/libgit2/libgit2.git /tmp/lg2-verify
    git -C /tmp/lg2-verify checkout 49e408b3208bc3093757a1c2db938d3590f3f412
    diff -r -q -x .git /tmp/lg2-verify libgit2
        # expect ONLY:  Only in /tmp/lg2-verify: .github
    # or, from the release tarball (GitHub regenerates tag archives, so its
    # sha256 may drift over the years; the tree inside is what matters):
    #   tar -xzf v1.9.7.tar.gz -C /tmp && diff -r -q /tmp/libgit2-1.9.7 libgit2
    #   -> the same single line

    git clone --branch v3.6.7 \
        https://github.com/Mbed-TLS/mbedtls.git /tmp/mb-verify
    git -C /tmp/mb-verify submodule update --init
    diff -r -x .git /tmp/mb-verify mbedtls           # expect no differences

That check is a convenience for a human, not a build step.
